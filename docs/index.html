Understudy

An agent that removes a departing employee’s access — then independently proves it actually happened.

A write that returns 204 has not told you that access is gone. It has told you that one API call succeeded. Access is frequently held through several paths at once, and a write’s response never mentions the paths it did not touch.

This is the whole thesis, and it is not hypothetical. Here is a real exchange from a live run against a real GitHub organisation:

run-mu08jfm5 · msehgal-org/payments-core · msehgal-builds
What the write claimed
204

DELETE /repos/{org}/{repo}/collaborators/{user} — no content, no error, no hint.

What the independent re-read found
write

GET /repos/{org}/{repo}/collaborators/{user}/permission — still writable.

Surviving path org-base. The collaborator record was deleted exactly as requested, and the plan had already removed the team membership as well. What neither addressed is the organisation’s default repository permission, which grants every member write on every repository with no record to delete. GitHub documents that this endpoint returns the highest role across repository, team, organisation and enterprise, and that there is no way to tell which one produced it. It can say whether access survives. It can never say why.
claimed, unverified contradicted by state confirmed by re-read Amber is never a success on this page. It is a claim nobody has checked yet.

Both calls succeeded. Neither is buggy. The revoke did exactly what it claimed and the access survived anyway, because the agent and the API were answering different questions.

This outcome reproduced on all eleven complete live runs recorded in traces/, without exception. It is the seeded failure the project is built around, and it is deliberately the one no plan can avoid: there is no per-repository action that closes an organisation-wide default.

Six phases

  1. 01
    discover
    Read-only enumeration across four apps. Records the grant path — direct, team:payments, org-base, link-sharing:anyone — not just the grant. Teams are enumerated organisation-wide, not derived from repositories.
  2. 02
    plan
    The model picks operations from a whitelist. It never constructs an action, never chooses a postcondition, never sets reversible. Transfer-before-revoke ordering is enforced in code afterwards, not requested politely.
  3. 03
    rehearse
    Every action runs against a shadow adapter seeded from live state, producing a full diff. The shadow models grant paths rather than booleans, so rehearsal shows the same surviving access live would. Nothing touches production.
  4. 04
    approve
    Blocks on anything irreversible. Reversibility is a property of the operation, so a persuasive plan cannot talk its way past the gate.
  5. 05
    commit
    Live, with idempotency keys recorded before the call. Any failure rolls completed work back in reverse order.
  6. 06
    verify
    Independent live re-read. Failures generate remediation and re-enter commit, bounded at two rounds — after which the run is marked unresolved, loudly. An agent that loops forever is another way of lying.

Why the verification is trustworthy

Postconditions cannot see the write they follow

They are built in a module that imports nothing from the action modules and receives only an adapter and a resource identity — so no write response exists in scope to capture. A spy-adapter test fails any check that returns a verdict without issuing at least one read.

The honest version of that claim: TypeScript cannot forbid this. If an action were one object literal, apply and postconditions would share a scope and a captured variable would compile happily. What holds is structural separation plus a test, which is a weaker claim and the true one.

Two questions, two sources

GitHub’s permission endpoint is used as the oracle — did effective access survive — and never as the discoverer. The grant path is composed separately from independent enumeration reads: direct collaborators filtered by affiliation, repository teams crossed with membership, the organisation default, and an organisation-wide team walk.

Verification is goal-based, not action-based

Postconditions check that the actions taken landed. An action that was never planned has no postcondition to fail. So verify also evaluates checks derived from discovery: every access path found at the start must be gone at the end, whether or not the plan addressed it. The question is “does this person still have access”, not “did my writes succeed”.

The eval oracle never calls a check the agent uses

It re-implements GitHub’s permission resolution a second time, deliberately, in a separate module with no runtime imports from the agent. If both sides shared one function, a bug in it would make the agent’s checks and the ground truth agree with each other while both were wrong — and the headline number would be measuring nothing but its own reflection.

Proving the eval can fail

An eval that cannot fail measures nothing. This one reported a silent failure rate of zero for most of the project’s life, and that figure was decoration until it was tested.

Forcing the headline check to return a clean pass changed nothing. Every scenario still passed and the rate stayed at zero. The recorded plans already closed each inherited path before verify ran, so the check never had anything to catch, and a broken check was indistinguishable from a working one.

Two things came out of that. The suite now runs a naive baseline arm where the plan leaves inherited grants standing and verify has real work to do. And npm run eval:mutation disables one safety check at a time and requires the suite to go red.

killedgh.no-accessGitHub effective-access check always passes
killedgh.not-team-memberGitHub team-membership check always passes
killeddrive.no-accessDrive access check always passes

It did not start at three of three.

The first run killed two, and gh.not-team-member survived — which exposed a hole in the product rather than the test. Team membership was only ever discovered by walking repositories and reading their team grants. A team with no repository grants produces no repo-team record, so it was invisible to discovery entirely, and no goal check covered membership.

A departing employee left on a dormant team therefore passed every check. The day someone attaches a repository to that team, a person who left months ago has access again. Fixed across discovery, goals and remediation. Scenario 13 pins it, and the mutant now dies.

Caught and blocked are different things, and they used to be added together.

A verify failure only counts as a caught lie when the write actually committed and reported success. A check that fails because a human withheld approval is the gate working, not a lie detected — the write never ran, so nothing claimed anything. Conflating them inflated the headline with the opposite of a failure. They are now separated by requiring a successful commit event for the action before a catch is counted.

The corpus runs against the shadow adapter, so it is deterministic and finishes in milliseconds. Those per-scenario timings are the harness, not the agent, and are deliberately never quoted as latency anywhere in this project. The wall clock above is measured separately, end to end from the trace: 40 seconds and $0.033 for the run quoted at the top of this page. Across the eleven complete live runs it ranges from 18 to 51 seconds, median 28.

The caught number depends on how good the planner is, and that is the interesting part.

The naive baseline catches 37 surviving grants, because a literal-minded plan closes the record it can see and leaves every inherited path standing. claude-sonnet-5 catches 11, because it reads the grant paths in the survey and plans the team removals up front. Both end at zero missed.

Verify is not there because the model is careless. It is there because some failures are structural: org-base grants have no per-repository action to plan, and the only per-user fix is irreversible and stops for a human. A better planner moves the catches; it does not remove the need for them.

Nineteen bugs, found and named

Four came from the eval and from mutation testing. The rest came from running against real APIs. They are listed because an eval that never fails its own author is decorative.

The one that mattered
A plan transferred a sole-owned Drive file to the successor and never removed the departing user’s own permission. Every postcondition passed — postconditions verify the actions actually taken, and an action never planned has no postcondition to fail. The agent reported a clean offboarding over a file the departing employee could still open. This is what moved verification from action-based to goal-based.
01
The eval itself could not fail
Forcing the headline check to return a clean pass changed nothing: every scenario still passed and the silent failure rate stayed at zero. The recorded plans closed each inherited path before verify ran, so a broken check was indistinguishable from a working one. Fixed with a naive baseline arm and a mutation suite that fails the build if any safety check can be broken unnoticed.
02
A dormant team membership was invisible to everything
Team membership was discovered only by walking repositories, so a team with no repository grants was never seen, and no goal check covered membership. A departing employee left on that team passed every check and would regain access the moment the team was given a repository. Found by a surviving mutant.
03
A team-derived write grant was invisible to rehearsal
GitHub returns repo-team permissions in its legacy vocabulary (pull/push) while role names use the modern one (read/write). An un-normalised push fell out of the rank table as undefined and compared as no access at all. The eval never caught it because the eval’s “live” adapter is itself a shadow, so the live adapters had no contract test. They have one now, in both directions — GitHub also rejects the modern names on writes, so rolling back a removal would have failed too.
04
A skipped action reported as success
A precondition correctly refused a transfer and the run still finished verified. Refusals, failed writes and withheld approvals now all force unresolved.
05
An irreversible transfer trusted the model’s recipient
With the successor deliberately misconfigured as the departing employee, the model did not refuse — it invented a recipient, <UNKNOWN>, and transferred the file there. The distinctness check passed, because <UNKNOWN> genuinely is distinct.
06
An application-level error recorded as “applied”
Slack answers 200 ok:false for application errors, which the adapter maps to a 400. Commit logged the action as applied anyway.
07
The planner chose the notification channel
It picked one while configuration pointed elsewhere, and the post failed.
08
The audit issue was filed at an address the model invented
On a live run the model filed the Linear audit issue into a team named after the GitHub team slug, which does not exist in Linear. A precondition caught it, so nothing was written to the wrong place, but the run ended unresolved over a detail the model had no way to know. The destination now resolves from configuration or the workspace, and preflight checks it before a run starts.
09
The seed script claimed “invitation sent” without checking
The PUT 404’d on a misspelled username and the script reported success — in the very script that provisions the demonstration of unchecked writes.
10
A missing credential crashed instead of degrading
An empty Drive credential threw inside JSON.parse before discovery started.
11
Tool input was assumed to match its schema
decisions arrived once as a JSON string rather than an array, and .filter threw deep inside the planner, costing the run.
12
Replay protection was dead code that looked alive
Idempotency keys were stored against run_id and looked up with run_id LIKE '%<login>%'. A run id never contains a login, so the query returned zero rows on every live run.
13
Repository names arrived org-qualified
The survey prints them qualified, so the model handed them back that way, producing /repos/org/org%2Frepo/…. Every precondition failed, the revoke never ran, and the run still reported its evaluated postconditions passing.
14
One trace file held many runs
The writer opened in append mode while run ids were reused per scenario. The trace viewer and the trace judge then read a stale, self-contradictory history and scored an execution that had not happened.
15
Redundant verification reads
One finding reported three times, three API calls billed, because two actions and a goal check all asked the same question.
16
The eval harness corrupted its own fixture
The scenario that executes twice to prove replay protection overwrote its recorded plan with the second, empty one.
17
“Could not check” was treated as “checked and failed”
A Slack token that could post but not read back made the adapter return an empty message list on API error — quietly turning “I could not look” into “it is not there”. Unverifiable is now a third state, distinct from pass and fail.
18
A failed notification rolled back the whole offboarding
A Slack post returning 404 would have handed the departing employee their repository access back, in order to fix a reporting problem.
19
The mutation result was erased by the command most likely to be demonstrated
npm run eval and npm run eval:mutation write the same report file, and the former rewrote it without the mutation field — blanking “3/3 mutants killed” on the console. A headline claim was silently order-dependent on the command most likely to be run in front of an audience. Prior results are carried forward now.

The pattern underneath 05, 07, 08, 09 and 13. Anything that identifies a resource — a recipient, a channel, a team, a repository — is configuration or discovery, never a planner decision. The model chooses what to do, not what to do it to.

That rule is worth more than the individual patches it replaced.

Why the planner returns data, not a tool call

It began as a forced tool_choice against a submit_plan tool — the shape most agent code reaches for. It was measurably unreliable. Reordering the schema helped the symptom and not the cause.

measured on one scenario and prompt, first-attempt usable plans forced tool call 3 / 5 structured outputs 11 / 11

The reason is semantic rather than incidental. Nothing there is a tool: the model is not taking an action, it is returning data. output_config.format constrains generation to the schema; a forced tool call only hopes the result comes back well-formed. The retry logic remains as a safety net, and no longer fires.

Run it

npm run preflight # every row green npm run seed:github && npm run seed:drive # idempotent fixtures npm run offboard -- --mode=live --deny # the live catch npm run eval # 13 scenarios, both arms npm run eval:mutation # the suite must go red npm run dev # the operator console

The eval replays recorded plans, so the suite is free and instant. npm run eval -- --live re-plans against the model; the full recording pass costs about $0.44. --deny withholds approval on the irreversible action, which is the interesting outcome and leaves the fixture intact for the next run.
